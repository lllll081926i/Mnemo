# 下载引擎审计（2026-10-04）

## 结论

目前不是每个网盘各有一套本地下载器：14 个插件负责获取下载源，普通下载统一走 `dlengine`。原实现确有客户端瓶颈：专用 UA 被覆盖，文件请求并发与任务数混用，光鸭因预览模式被误降为单请求，暂停恢复丢失完整下载策略。已修复这些问题，并核查目录同步和跨盘迁移的下载路径。

**代码审计和本地验证完成，不等于 14 个网盘公网满速验收。** 本次没有真实账号的套餐、CDN、时段、带宽与磁盘测量；不能给出官方连接数或速度上限，更不能承诺突破会员限速。

## 已修复的问题

| 问题 | 原行为 | 修复后 |
|---|---|---|
| 网盘 UA | 下载器默认 UA 覆盖插件 UA，迅雷移动端 UA 实际未生效 | 默认保留插件 UA，显式 `Options.UserAgent` 可覆盖；大小写不敏感 |
| 文件并发 | 同时下载 1 个文件就只有 1 个分片请求，最多 4 | 新增独立设置，默认 8、范围 1–16，任务队列仍默认 3 |
| 代理模式 | `proxy` 预览策略隐含单请求；redirect 的显式限制被忽略 | 只依据插件的显式 `Concurrency` 上限；不把预览代理当作本地下载限制 |
| 分片策略 | 插件 `ChunkSize` 未消费；32 MiB 文件默认只有 2 片 | 消费显式分片大小；默认按文件大小与并发自适应为 1–16 MiB |
| 暂停恢复 | 缓存 URL 导致不再取得头、鉴权器和限制，还可能复用过期签名 | 账号任务每次启动重新取得完整下载源；直接 URL 任务保留用户输入 |
| 空闲超时 | 正文读取长期不响应也不超时 | 每次阻塞网络读取默认 60 秒空闲超时；限速等待、磁盘写入与上传方背压不计入 |
| HTTP 重试 | 401/403/404 等重复等待，429 无视 Retry-After | 永久 HTTP 错误立即返回；408/429/5xx 最多 5 次；同一下载共享退避；等待可取消 |
| 请求鉴权 | 重新发送临时失败的请求可能复用旧 Digest nonce count | 同源重试重新执行请求鉴权；不在跨域重试时重新附加源站鉴权 |
| 分片调度 | 每一片一个 goroutine，大文件产生大量等待线程 | 固定数量 worker，峰值受配置控制 |
| 检查点 | 每片同步写 JSON、忽略失败；分片数据未先持久化 | 最多每秒合并检查点，先同步数据再写状态；暂停/失败也保存；错误明确返回 |
| 分片恢复 | 更改默认分片策略会放弃原断点 | 自动分片模式保留匹配资源的已有合法分片布局 |
| 全局限速 | 旧窗口重置可忽略仍在等待的额度；修改设置不唤醒旧等待 | 共享令牌桶，约 100 ms 突发额度；设置变更立即唤醒等待；普通下载、同步和迁移共享额度 |
| 退出时序 | Shutdown 发出取消就返回，任务落盘线程尚未结束 | 阻止新 worker，等待现有文件/目录 worker 收尾，避免退出时遗漏状态写入 |
| 文件替换 | Windows 回退路径可能把目标目录移走 | 目标必须是普通文件；拒绝替换目录或符号链接 |
| 123 下载入口 | 中转 GET 不走应用/系统代理，且最终源未携带入口 UA | 中转使用 `netx.NewClientWithSystemProxy`，返回 Referer 与专用 UA |
| 光鸭下载头 | Referer 错写为夸克域名 | 使用光鸭官网域名和已有 UA |
| PikPak CDN | API Bearer token 被转发给签名下载 URL | 元数据 API 保留鉴权，签名 CDN 下载不附带账号 token |
| Dropbox 过期时间 | Unix 秒，与其他下载源的毫秒约定不一致 | 统一 Unix 毫秒 |
| 目录同步 | 无条件单请求，也未使用下载设置和全局限速器 | 共用设置与限速器，尊重网盘上限，并传递大小、头、鉴权和分片参数 |
| 跨盘迁移 | `netx.NewClient(0)` 实际是 60 秒总超时，不是无限时长 | 使用下载专用 HTTP 客户端，无总超时、有空闲超时；使用全局限速器并核对已知大小 |

### 保留的边界

- 六个插件的 `Concurrency: 1` 属于现有保守兼容策略，没有足够证据说明它们是官方硬限制。此次不做盲目增连接，避免验证失败或封禁；这也是下一轮真实账号测速最值得检查的项目。
- 无 Range 的大文件不能安全分段或复用分片断点，单流读取中断不会自动从零反复下载整个文件。支持 Range 的分片仍有有界网络重试和短响应续接。
- 账号任务的 401/403 会重新取下载源一次；真实权限不足也可能是 403，刷新一次后仍失败就报告，不能靠循环刷链接解决。
- 同一稳定文件换签名 URL，只有资源身份与 ETag/Last-Modified 验证匹配时复用断点；没有验证值时宁可重新下载，不拼接未经验证的旧内容。
- 跨盘迁移的管道与临时文件回退仍为顺序流；管道速度受目标上传背压制约。临时文件回退尚未改为多请求下载，属于后续性能优化项，不声称本轮已并行化全部迁移路径。
- Retry-After 超过 120 秒时直接报告 HTTP 错误，不提前重试；退避目前在单个下载 HTTP 客户端内协调，尚未实现跨账号/跨任务共享的服务商级退避。
- 实时预览代理不是本地保存的下载器。不能把视频预览成功或速度当作本地多分片下载测速结果。

## 可复现的性能证据

命令：`go test ./internal/transfer/dlengine -run TestDownloadParallelPerformance -count=1 -v`。

使用本地 32 MiB 数据源，每个请求每 10 ms 最多传输 256 KiB；下载结束逐字节核对，并核查有效并发确实为 1/8。一次独立运行结果：

| 请求并发 | 耗时 | 吞吐 |
|---|---|---|
| 1 | 1.512 秒 | 21.16 MiB/s |
| 8 | 0.216 秒 | 148.17 MiB/s |

该受控场景约 **7.00 倍** 提速，证明客户端不再因默认分片不足而只能发出 2 个请求。它不代表任一网盘的公网速度；共享总带宽限制下增加请求可能没有收益，甚至增加 429。

## 公网验收方法

每个账号选择相同大小的原文件（建议至少 512 MiB），固定代理、出口和保存磁盘；分别测单请求与允许的 2/4/8 请求，记录整段传输时间、持续速度而不是瞬时峰值。至少重复 3 次并校验哈希，同时记录 401/403/429、Retry-After、Content-Range、套餐与时间段。遇到 429 不继续增连接；遇到代理瓶颈应对比直连与代理，不频繁切换设备或反复登录。
