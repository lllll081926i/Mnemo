# Mnemo-Go 全量项目审查报告（2026-08-20）

## 1. 审查结论

审查对象为 `D:/Code/Mnemo/Mnemo-Go`，审查基线版本为 `v0.2.0`，修复以本报告和本地提交历史为准。本次没有读取 `D:/Code/Mnemo` 中的旧项目或参考示例，没有登录或请求任何真实网盘账号，也没有使用浏览器做视觉验收。前端结论仅来自源码、数据流、构建结果和 Wails 绑定链路。

项目的基础架构已经成形：13 个 Provider 已接入统一驱动层，下载、上传、迁移、同步、预览和本地存储均有可运行实现；全量编译、后端测试、静态检查和核心竞态检查均能通过。审查最初发现的四项 P0 已全部关闭并补回归测试；同步任务重入、上传 worker 生命周期、共享限速、敏感下载状态、本地预览越权、DNS rebinding、外链协议、Provider 主链路取消和迁移部分结果误报也已关闭。按自用项目要求，更新产物不再使用独立签名密钥或 GitHub Actions 签名 secrets；系统凭据库、WebDAV 非 Basic 认证和真实平台/服务商验证仍受外部条件限制。

发布安装包的应用显示名统一为 `Mnemo`；版本号仅作为包管理器的独立版本字段和升级比较依据，不拼接到开始菜单、桌面快捷方式、安装目录、卸载项或 Linux desktop/AppImage 的应用名称中。Windows Inno 的版本字段由 release tag 注入，避免继续使用旧的硬编码版本。

## 4. 风险分级

严重度定义：

- P0：可能越界读写、误删、损坏文件或让用户无法安全恢复，必须优先修复。
- P1：明显安全、稳定性、并发或发布质量风险，应在下一稳定版本前关闭。
- P2：功能一致性、可维护性、可访问性和规模化体验问题，应进入明确迭代计划。

## 5. WebDAV `PROPFIND 530` 专项

### 5.1 已确认的代码原因

原实现存在三个会显著增加 530/认证失败概率的问题：

1. Endpoint 的目录尾斜杠会在根请求中消失，例如用户配置 `/dav/`，实际请求 `/dav`。
2. 连接校验失败只返回 `webdav: PROPFIND 530`，丢失服务端给出的认证方式、正确地址或应用密码提示。
3. WebDAV 使用独立 `http.Client`，没有继承应用全局代理。

三项均已在本轮修复。连接校验仍只发一次 `Depth: 0 PROPFIND`，不会为了“猜认证方式”连续轰炸服务端。

### 5.2 530 应如何解释

HTTP/WebDAV 标准没有定义通用的 530 语义。它可能由服务商网关、反向代理或安全系统自定义，常见类别包括：

- WebDAV Endpoint 填成了网页登录地址；
- 严格要求集合 URL 末尾 `/`；
- 必须使用应用密码而非网页登录密码；
- 账号区域、套餐或 WebDAV 功能未开启；
- 服务端只允许 Digest/特殊认证，而当前客户端仅支持 Basic；
- IP、设备或短时间请求触发服务端风控。

修复后的错误会保留安全诊断。例如服务端返回 `WWW-Authenticate: Digest` 时，用户可以看到认证方式不兼容，而不是继续反复尝试密码。

### 5.3 仍需现场信息才能确认的内容

要定位用户的具体 530，至少需要服务商名称、填写的 Endpoint（可隐藏域名中的个人部分）和修复后显示的诊断文本；不需要提供账号或密码。由于本轮没有请求真实账号，不能承诺仅靠尾斜杠修复就一定解决该服务商问题。

### 5.4 容量标准

WebDAV 容量使用 RFC 4331 定义的 `DAV:quota-used-bytes` 与 `DAV:quota-available-bytes`。它们是可选属性，服务端返回 207 但属性 404、或明确不支持时，Mnemo 显示未知，不回退为递归扫描。参考：[RFC 4331](https://www.rfc-editor.org/rfc/rfc4331)。WebDAV 核心协议参考：[RFC 4918](https://www.rfc-editor.org/rfc/rfc4918)。

## 6. S3 专项

原实现只调用 `HeadBucket`。AWS S3 在调用者没有相应 bucket 权限时可能统一返回 403；一些 S3 兼容实现也不完整支持该操作。因此“AK/SK 能在指定前缀读写”与“HeadBucket 成功”并不等价。

本轮策略：

- 正常情况只发一个 `HeadBucket`。
- 仅在 403/405/501 时追加一次 `ListObjectsV2`，限制 `MaxKeys=1` 并使用配置前缀。
- 两次都失败时同时保留两种错误，便于判断 Endpoint、Region、签名、Bucket 和策略问题。
- SDK 最多 2 次尝试，HTTP 超时 60 秒，并继承全局代理。
- 不通过 Put/Delete 创建测试对象，避免连接校验产生副作用。

AWS 官方操作语义参考：[HeadBucket](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadBucket.html) 与 [ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html)。

### 7.1 当前风控友好策略

- 前端账号级进行中请求合并；同一账号一小时内不会重复触发。
- 首次刷新延迟 30 秒，避免和登录流程紧挨；窗口隐藏时不刷新。
- 后端再做账号级 `singleflight`，即使多个组件或未来调用者同时触发也只执行一次。
- 成功结果缓存 45 分钟；普通错误退避 10 分钟；包含 429、rate limit、captcha、风控、频繁、限流等信号时退避 60 分钟。
- 普通 Provider 登录成功后立即写入刷新缓存，避免头像组件重复刷新 token 和配额。
- WebDAV 容量不做多种属性/目录回退；S3 容量不做对象扫描。

Provider 现在可通过 `RetryAfter() time.Duration` 提供精确冷却，账号刷新会采用默认风控冷却和服务端要求中较长的一项；PikPak 已接入该契约。后续仍应把 `Retry-After` 解析提升到统一网络层，加入指数退避和随机抖动；缓存“服务端明确不支持容量”状态，避免每小时重复探测；PikPak 的 token 续期与容量读取应彻底解耦，只有 token 接近过期才续期。

建议门禁分阶段实施：先要求所有 P0/P1 修改具备回归测试且关键安全模块达到 60%；再把 changed-lines 覆盖率提高到 80%。不要为了总体数字给简单格式化函数堆测试。

## 12. 下一步值得做的产品功能

以下功能优先级高于继续盲目扩充 Provider 数量：

1. **连接诊断页**：测试 Endpoint、认证方式、重定向、根目录、读权限和可选写权限；显示本次实际请求数，导出脱敏诊断。WebDAV 530 和 S3 403 会因此更容易定位。
2. **同步预演与恢复**：运行前展示将上传/下载/删除的清单，支持冲突策略、删除阈值、快照版本和失败恢复。它也是让同步从“能跑”变成“可放心用”的核心功能。
3. **统一账号健康中心**：显示登录有效性、容量、上次刷新、冷却截止时间、Provider 服务错误；手动刷新仍由后端限频。
4. **传输目标冲突中心**：下载和上传统一处理覆盖/保留两者/跳过，并展示文件完整性和重试原因。
5. **账号移除向导**：选择仅移除凭据，或同时清理同步、任务、收藏、缓存和上传会话。
6. **Provider 可验证能力页**：把“声明支持”与“最近一次 mock/真实服务验证”分开，避免 95% 这类无法行动的数字。
7. **供应商特定容量插件**：只在供应商有明确、低成本配额 API 时接入；S3 不提供通用容量扫描。
