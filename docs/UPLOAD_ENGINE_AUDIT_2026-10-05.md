# 上传引擎审计（2026-10-05）

## 结论

已逐项检查 14 个驱动、上传队列、全局限速、会话保存、目录同步和跨盘迁移。当前 13 个驱动实现上传，迅雷仍未实现上传，不能因为已有网盘接入就开启上传按钮。

上传确实存在客户端问题，不只是网络或会员限制：PikPak 指纹被重复编码；OneDrive 把最后一个分片的接收当成文件提交完成；光鸭取消时可能提前返回并关闭仍在使用的文件；多个哈希路径不响应取消；断点和进度存在错误。本轮已修复可明确复现的这些问题。

**这不是“所有网盘上传已满速、所有问题已解决”的结论。** 仍有总超时、同名策略和会话恢复一致性等需要后续处理的问题。没有真实账号写入或公网测速，不能给出官方最大并发、实际 Mbps 或突破会员限制的承诺。

## 架构与速度限制

- 普通文件上传共用 `internal/transfer/upload.go`。WebDAV/S3 的 `direct` 是驱动上传方式，不代表它们另有无限并发队列。
- 上传任务数沿用 `MaxConcurrentDownloads`：正常设置默认 3，读取设置失败时回退 2；队列创建后不会随着下载并发设置即时改变。
- 除光鸭 OSS 的 2 个分片 worker，现有单文件分片上传基本串行。任务并发与分片并发不同，也与 HTTP/2 连接数不同。
- 正文发送经过 `netx.DoUpload` / `UploadHTTPClient`，共享 `MaxUploadSpeed` 额度；取消和修改限速能唤醒等待。多个任务不能各自获得一份全局额度，重发正文也会计入流量。
- 上传前哈希不受网络限速影响，但会占用本地磁盘和 CPU。暂停恢复时重新计算实际内容，比复用不可信的旧哈希更安全。
- 同步和跨盘迁移直接调用同一驱动上传处理器，不经过普通上传队列的 semaphore；共享网络限速，但不共享该队列的任务数上限。当前没有驱动实现可直接消费流的 `UploadStream`，迁移上传仍需要本地文件。

## 已修复

| 问题 | 原行为 | 本轮结果 |
|---|---|---|
| PikPak GCID | 将 40 位十六进制字符串再次按字符编码成 80 位，上传指纹错误 | 恢复一次编码；空文件、单块和多块有独立回归 |
| 本地哈希取消 | PikPak、123、优享蓝奏、天翼、阿里和 S3 的部分路径继续读完整文件 | 检查操作 context；有 UI 停止回调的路径同时检查回调；蓝奏临时正文复制也可取消 |
| 上传源短读 | 123 接受不足长的片；天翼、优享蓝奏把短读当成功，甚至将缓冲区零值计入哈希 | 要求读满计划分片；OneDrive/Dropbox 同样拒绝不足长的本地内容；S3 总字节数不一致时禁止提交 |
| OneDrive 完成条件 | 最后一片收到 202 或缺少文件 ID 的 201，也清除检查点并成功返回 | 必须取得有效的完成文件 ID；未确认保留会话，首次发送前就保存会话 |
| 天翼完成条件 | 提交响应缺少文件 ID 仍返回成功 | 缺少 ID 返回明确错误；空文件也可报告进度，使用实际文件大小 |
| 阿里续传进度 | 初始已累计完成片，循环又加一次，后续未传完就显示 100% | 已完成片只计算一次，不再次增加字节数 |
| 阿里旧哈希 | 失败任务保存的 SHA1 可以在本地文件改变后继续使用 | 每次上传核查实际 SHA1；OneDrive/Dropbox 的会话标识同时包含修改时间，不能只信传入哈希 |
| Dropbox 小文件授权 | 分片支持续期，小文件没有同等处理；请求关闭文件后无法重放 | 过期令牌只续期一次，保留调用方文件，重放完整正文并设置长度；不可重放输入明确报错 |
| Dropbox 会话提交 | 单片会话重复发送已经 start 的内容；完整偏移无法续办提交；恢复会话遇临时错误也被丢弃 | 用空正文提交已发送内容；完整偏移可提交；只有明确的会话不存在错误才能重建 |
| 光鸭分片取消 | 提前返回、文件被关闭，仍有上传 goroutine；首次失败后继续调度后续片 | 固定 2 个 worker；取消兄弟请求、等待全部收尾后返回；失败和提交失败均做限时 abort |
| 光鸭 OSS 检查 | 缺失上传 ID/ETag 未被可靠拒绝；大文件分片数可能超出客户端计划范围 | 校验 ID/ETag；分片计划控制在 10000 片以内；此数字是客户端计划约束，不是已验证的光鸭账号限制 |
| 光鸭结果与代理 | task 查询取得文件 ID 后丢弃；OSS SDK 路径不跟随应用代理设置 | 保存远端文件 ID；OSS SDK 使用统一 HTTP 客户端和代理 |
| 一刻异常分片 | 负数被跳过，超出范围的分片可能导致负长度缓冲区 | 无效分片序号立即失败，哈希检查 context；登录入口仍保持隐藏 |
| 重启排队任务 | 恢复时显示 queued，但没有对应 worker | 未完成任务统一恢复为可手动继续的 paused，清零旧速度 |
| 退出上传队列 | 只发送取消就返回，worker 尚未落盘 | 阻止新 worker，等待收尾，再保存未完成任务；重复关闭安全 |
| 上传状态与事件 | 共享任务指针、迟到进度覆盖暂停检查点；速率长期为零，失败事件缺少原因 | 队列持有任务副本；落盘核查最新状态；按进度样本计算速度；事件包含账号、网盘和错误 |

速度显示是驱动已报告字节的短时间平均值：串行大分片仍可能呈跳跃变化；它不是独立测得的线上 socket 即时速率。

## 遗留风险与建议顺序

### 优先级 1：正确性与大文件可靠性

1. **统一正文超时语义。** 多条上传路径仍有 60/90/120 秒或 5/10 分钟的 `http.Client.Timeout`，它覆盖完整正文发送和全局限速等待，不只是“连接超时”。例如蓝奏 100 MiB 在 1 MiB/s 上传约需 100 秒，现有 60 秒超时会失败。不能只把 Timeout 清零：还必须补发送停滞、响应空闲超时和取消，并用低速、背压、断网测试验证。
2. **同名策略必须和 UI 一致。** 移动固定自动改名、天翼固定非覆盖；蓝奏、优享蓝奏、光鸭、一刻没有完整消费统一 ConflictPolicy。PikPak overwrite 在新上传成功前把旧文件移入回收站。应按可验证的 API 实现 overwrite/rename/skip/refuse，否则收紧能力声明，不继续展示无效选项。
3. **服务端会话对账。** 除 S3、OneDrive 的部分处理，多数驱动依赖本地已完成片。需要分清会话失效、签名到期、429/临时网络失败、最后提交已经成功但响应丢失。创建/完成操作不能简单重发，否则可能重复文件；PikPak、光鸭、WebDAV 的“继续”目前是重新上传，不是真断点续传。
4. **同目标并发与上传记录。** 重复任务、目录同步和迁移可能同时写同一目标；一些 provider 的 session key 未包含冲突策略。会话 JSON 相同 key 使用相同 `.tmp`，当前仅读取全局目录时加锁，不能保证并发保存同一 key 的安全。应增加目标互斥或会话所有权与原子保存锁，再测跨流程并发。
5. **目录任务恢复的父目录。** 队列首次上传会把远端最终父目录写回任务，但保留完整相对路径。失败后恢复时可能从最终父目录再次创建同一路径，形成重复嵌套目录；应分开保存原始目标根目录与解析后的父目录，不能只修改进度。

### 优先级 2：性能、反馈与目录完整性

- 为上传单独设置任务并发，并让同步/迁移遵守统一调度；目前修改下载并发不热更新上传队列。
- 仅对已验证可并行的片协议增加小规模 worker 池，串行强约束协议继续串行；不对全部网盘强行开启 8/16 路。
- 使用确认字节与发送字节分开的进度指标，补齐小文件/单 PUT 和大分片内的连续反馈；避免把“已读入发送缓冲区”当成“服务端已持久化”。
- 上传会话多数保存错误被忽略；应明确降级为不可恢复或失败提示，不能承诺未持久化的断点可恢复。
- 目录上传忽略空目录；部分扫描错误被跳过，目录缓存全局串行，远端父目录查找只读取当前分页；需补空目录任务、扫描失败提示和完整分页查找。
- 清理已结束上传时，内存跳过仍在收尾的 worker，但持久化清理按终态标志删除全部记录；需统一按具体任务 ID 清理。
- 对会话 URL、临时上传凭证的保存期限和敏感信息脱敏继续审查；本轮没有将临时 STS 密钥加入持久化。
