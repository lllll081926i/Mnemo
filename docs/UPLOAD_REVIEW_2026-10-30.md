# 上传异常专项审查

日期：2026-10-30。源码基准：`8dc22c0`。关联总报告：[项目全貌与审查记录](PROJECT_REVIEW_2026-10-30.md)。

本轮以用户提供的阿里云盘上传截图为入口，先审查基线的 14 个驱动，再按用户要求实施修复并移除一刻相册。当前保留 13 个驱动。以下 F8–F15 和 7 项缺陷探针记录的是修复前表现；当前结果以本节为准。没有调用真实网盘账号。

## 0. 当前实现

| 秒传路径 | 本轮确认规则 |
|---|---|
| 阿里云盘 SHA1 | 识别结构化 `PreHashMatched`，本地文件提交 proof_code；`rapid_upload=true` 必须有文件 ID；`exist=true` 需要核对目标文件 SHA1、大小、父目录和类型；哈希未命中复用同一上传会话。 |
| PikPak GCID | 明确完成阶段或读取详情确认完成；缺少 resumable 参数不再直接认为成功。 |
| 123 MD5 | Reuse 必须返回有效文件 ID；未命中保存完整会话供本地上传复用，保存失败立即停止。 |
| 移动个人云 SHA256 | 秒传必须有真实目标文件 ID；未命中保留会话，缺少完整会话返回错误；家庭云不声明哈希秒传。 |
| 天翼 MD5 | `fileDataExists=1` 后仍需提交，提交回执必须有目标文件 ID；不能仅凭已有数据返回成功。 |
| 优享蓝奏 MD5 | 无 upToken 且有文件 ID 才是秒传；两者都没有时返回不完整回执错误。 |
| 光鸭服务端去重 | code=156 接受直接文件 ID，或按 taskId 查询到允许的业务状态和真实文件 ID；错误状态附带 ID 不算成功。 |
| 迅雷 GCID | 明确完成阶段接受秒传；空参数时读取详情；未命中用 S3 PUT/multipart，等待文件完成确认。没有新增仅凭哈希的跨盘秒传入口。 |

其他 5 个驱动（OneDrive、Dropbox、普通蓝奏、WebDAV、S3）没有新增专有秒传能力。全部 13 个驱动都在前置检查后、首次写入前调用 `BeginUploadAttempt`，消除“没有打开本地文件也进入待核对”的公共问题。远端已完成后的凭据保存失败通过 `upload:warning` 通知，不再把完成上传变为失败。

通知：全局监听上传/下载失败和迁移失败，传输页未打开时也能收到通知。传输页和全局监听共享去重；恢复后再次失败或错误改变会重新通知。任务行不再显示原始报错、内部错误码或三角展开建议，只保留“查看通知”。真正未知结果继续要求核对，原有防重机制保留。

本轮 F8、F10、F12、F14 已修复。F9 已修复前置检查误标记和成功凭据保存误报；远端写入后的不明错误仍保守保留未知状态。F11 已提前保留阿里/移动 ID、使用阿里实际返回名称、补充 GCID 内容核对；中途退出前的 worker 身份没有新增通用持久回调，仍属部分修复。F13 已接入前端策略筛选并修复 Dropbox skip；其他驱动的冲突策略未全面统一。F15 已在驱动入口拒绝虚拟根上传并说明应选择真实空间。

一刻相册已完全退出支持范围：移除驱动包、注册、常量、图标、登录入口与在役文档。旧源码移至被 Git 忽略的 `.trash/removed-yike-20261030/`，没有硬删除用户文件或清空用户账号。

最终检查：全量 Go 测试、竞态测试、vet、前端 302 项测试、前端构建、Windows 桌面构建与 Go 漏洞扫描通过。新增实际驱动回归覆盖上述完成条件、缺少身份、未完成回执、同会话回退、结构化错误、完成回执丢失后只读核对、凭据保存失败及检查点失败。浏览器覆盖通知、侧栏滚动/缩放和账号排序。真实服务端账号、套餐、风控与大文件时长仍需实测。

## 1. 截图能说明什么

`UPLOAD_RESULT_UNKNOWN` 是应用生成的状态码。它不是阿里云盘返回的错误码，也不能证明文件已经上传成功。用户补充的“处理建议”仍是同一份通用提示，没有包含原始失败原因。

截图中的文件约 124.1 MB。当前阿里驱动对此大小使用 20 MiB 分片，约需 7 片；没有发现针对 PDF 或 124 MB 的本地上传禁令。`netx.DoUpload` 会移除普通 HTTP 客户端的整体超时，不能仅根据 `clientOf` 的 60 秒配置断言这是上传耗时过长造成的失败。

修复前基线链路：

```text
公共门面锁定目标名称
  → 保存 pending 提交记录
  → 驱动校验会话、打开文件、计算哈希、初始化、上传、完成确认
  → 任意非 nil 错误都写成 unknown
  → 前端用通用 issue.message 替代原始 failedMessage
  → 显示“待核对”
```

因此，尚未发出网络请求的失败、服务端明确拒绝、分片中断、完成回执丢失和本地保存失败，都可能表现为截图中的相同提示。

本轮只在项目现有 `build/bin/data/logs/mnemo.log` 中定向检查了上传失败记录，没有找到与该任务对应的条目。没有读取账号凭据。**当前证据可以确认下面的代码缺陷，不能确定截图这一次上传最初在哪一步失败。**

## 2. 新增发现

### F8 / P1：阿里云盘父目录 ID 被重复编码，破坏自动核对和后续目录查询

定位：`internal/drive/providers/aliopen/aliopen.go:407`、`:1512`、`:1682`、`:1707`、`:2479`；`internal/transfer/upload_receipt.go:132`。

`mapFile` 会给父目录加空间前缀，但 `List`、`GetInfo`、`Search` 的部分调用方已经传入统一目录 ID。`wrapRef` 没有处理已有前缀或虚拟根。

已复现：

| 输入目录 | 返回的父目录 |
|---|---|
| `b:parent` | `b:b:parent` |
| `r:parent` | `r:r:parent` |
| `backup_root` | `b:backup_root` |
| `resource_root` | `r:resource_root` |

端到端探针模拟“完成回执丢失，远端文件实际存在”。远端文件 ID、名称、大小、SHA1 均匹配，真实驱动仍返回 `b:b:parent`。队列要求父目录等于原始 `b:parent`，所以拒绝完成核对。首次查询还会记住错误父目录；随后 `GetFileFreshContext` 可能使用该父目录重新列举，进一步造成查询失败。

修复应统一原始 ID 和统一 ID 的边界，分别核验备份盘、资源盘、空间根、普通目录、列表、分页、详情、搜索和恢复。仅放宽核对时的父目录比较会掩盖映射错误。

### F9 / P2：公共提交状态过早进入 pending，所有驱动的错误被过度归入未知结果

定位：`internal/drive/ops.go:942`；`internal/transfer/upload_receipt.go:35`、`:68`；`internal/transfer/upload.go:701`。

门面在整个 `UploadOneFile` 之前调用 `BeginUploadAttempt`。`finishUploadAttempt` 没有区分“未提交”“服务端明确拒绝”和“提交后回执丢失”。任何非 nil 错误都会变成 `unknown`。

已用真实阿里驱动和真实队列复现：无效本地会话导致 **0 次网络请求**，任务仍进入 `UPLOAD_RESULT_UNKNOWN`，普通恢复也被拒绝。另用模拟 HTTP 400 明确拒绝复现相同状态。

影响范围是公共队列中的 13 个可上传驱动。迅雷当前关闭上传，正常界面不适用。需要由驱动报告提交阶段或返回明确的提交结果类型，在第一项可能改变远端状态的操作前持久记录。确实不明的结果仍必须保留防重保护。

### F10 / P2：前端隐藏上传原始错误，使鉴权、网络和分片问题无法从该界面诊断

定位：`frontend/src/task-notices.js:3`；`frontend/src/views/TransferView.vue:292`、`:1197`；`frontend/src/components/TaskIssue.vue:30`。

后端保留了 `failedMessage`，但 `taskErrorText` 优先返回 `issue.message`。上传列表正文和悬停文字都走这一函数。“处理建议”只显示通用问题、操作建议和状态码。现有下载任务详情没有接到上传行。

这解释了用户展开后只能提供通用提示。应同时展示“提交结果”和经过脱敏的“原始失败原因”，保留可复制详情，并按原始错误提供重新登录、代理设置、磁盘检查等操作。

### F11 / P2：回执恢复所需的文件身份和哈希契约没有逐盘闭合

定位：`internal/transfer/upload_receipt.go:79`、`:123`、`:135`；各驱动上传实现，见下一节。

自动核对必须有 `attempt.FileID`，并要求远端提供 MD5、SHA1 或 SHA256。当前许多驱动只在成功返回前写入文件 ID；完成请求或最终轮询失败时，队列便没有查询入口。蓝奏云、一刻相册的上传路径始终没有写回统一文件 ID。

阿里有独立缺口：创建结果中的 `file_id` 已进入分片会话文件，但直到保存会话和 `fillUploadURLs` 成功后，才赋给 `ui.Upload.FileID`。已模拟获取地址失败，确认分片会话有 ID、任务回执却无 ID。

此外，执行中的文件 ID 只保存在 worker 副本中，通常等驱动返回后才进入任务回执。中途进程退出时，队列没有通用途径从分片会话恢复该 ID。部分服务商返回的专有哈希也不在核对支持范围内。

阿里使用服务端 `auto_rename` 时，还没有解析实际返回文件名；回执仍保存请求名称。若服务端改变名称，恢复时的严格名称比较会增加核对失败。这一分支为静态确认，未做真实账号重名上传。

修复应建立驱动可用的持久回执更新接口，记录远端 ID、会话 ID、实际名称和提交阶段；对专有哈希提供明确核对能力。不能用“同名且同大小”代替内容证明。

### F12 / P1：Dropbox 的 skip 策略存在覆盖其他客户端新文件的窗口

定位：`internal/drive/providers/dropbox/onedrive.go:290`；`internal/drive/providers/dropbox/dropbox.go:509`。

驱动先以 `mode=overwrite` 初始化策略。`skip` 只先查询目标；查询返回不存在时没有改变写入模式。已捕获真实驱动构造的上传请求，确认 `ConflictPolicy=skip` 最终发送 `mode=overwrite`。

若另一客户端在查询后、提交前创建同名文件，当前请求具有覆盖该文件的语义。进程内目标锁不能约束其他客户端。该缺陷既影响小文件上传，也影响复用相同策略的分片提交。

应让 skip 在服务端使用拒绝覆盖的提交条件，将明确的同名冲突处理为跳过，并保留真正不明结果的防重保护。本轮复现了请求模式，没有在真实账号上执行覆盖。

### F13 / P2：界面提供统一冲突选项，但部分驱动没有执行相同契约

定位：`frontend/src/views/PanView.vue:1299`、`:2218`；`internal/drive/capabilities.go:75`；以下驱动代码。

| 驱动 | 代码行为与界面承诺的差异 |
|---|---|
| 移动云盘 | 个人云上传固定 `fileRenameMode=auto_rename`（`pan139.go:1755`），不读取 `ConflictPolicy`。家庭云也固定参数。选择覆盖、跳过或拒绝没有对应实现。 |
| 天翼云盘 | 两处 `commitMultiUploadFile` 都传 `overwrite=false`（`upload.go:367`、`:417`），没有使用上传策略，虽然提交函数已有覆盖参数。 |
| 123 云盘 | `duplicateFromPolicy` 只区分覆盖和其他策略（`pan123.go:1628`）；skip、refuse 没有独立的跳过或拒绝检查。 |
| 优享蓝奏、光鸭、一刻、普通蓝奏 | 上传路径没有读取 `ConflictPolicy`。实际同名行为交给服务端；界面不能据此保证“跳过”或“覆盖”。 |
| PikPak | 已有明确的安全拒绝覆盖逻辑，但前端仍显示“覆盖”选项，错误随后又可能被 F9/F10 隐藏。 |

前端冲突弹窗固定显示覆盖、重命名、跳过，没有按 `UploadConflictPolicies` 筛选。文件夹上传预检只比较根层名称，没有逐文件预检已有目录内部的冲突，因此后端策略更不能依赖这个弹窗兜底。

修复应先准确声明驱动能力，再落实队列和驱动契约。没有安全覆盖能力的驱动应明确拒绝或隐藏覆盖。不能通过先删除原文件实现所谓安全覆盖。

### F14 / P2：Dropbox、123 和移动个人云忽略续传检查点保存失败

定位：`dropbox/dropbox.go:638`、`:667`；`pan123/upload.go:307`、`:407`；`pan139/pan139.go:1786`、`:1848`。移动秒传探测另见 `:1913`。

这些位置使用 `_ = drive.SaveUploadSessionState(...)`。磁盘满、目录权限或原子替换失败都不会阻止继续提交。

已用 Dropbox 的实际分片上传函数注入存储失败：2 次检查点写入均报错，驱动仍执行完成提交并返回成功。该探针没有模拟进程崩溃；可确认的是程序无视了“续传信息并未可靠保存”，不能据此直接断言已发生数据损坏。

阿里、OneDrive、天翼、S3 的主要上传路径已检查相应错误，优享蓝奏也传播保存错误。建议统一检查并保留源文件、已有远端会话和原始失败原因。

### F15 / P2：阿里虚拟根仍可上传，内部哨兵值被作为真实目录 ID 提交

定位：`frontend/src/views/PanView.vue:1874`；`internal/app/app.go:1570`；`internal/drive/providers/aliopen/aliopen.go:383`、`:1633`、`:1982`。

`aliopen_root` 表示包含备份盘和资源盘的虚拟视图。当前上传按钮没有排除该视图；后端也没有要求选择实际空间。`parseRef` 将 `aliopen_root` 当成备份盘普通 ID，创建请求因而携带 `parent_file_id=aliopen_root`。

已用实际队列和驱动捕获该请求。模拟服务端明确拒绝后，任务仍被 F9 转为“待核对”。这是一条可能产生截图状态的确定代码路径；没有证据表明用户此次就在虚拟根操作。

应在虚拟根要求选择备份盘或资源盘，并在驱动入口拒绝虚拟根写入。不要静默猜测目标空间。

## 3. 14 个驱动对照

“会出现待核对”指进入公共提交回执后发生错误时会进入此状态，不表示该驱动每次上传都会失败。“恢复限制”描述当前实现，不能视为真实服务商验收结论。

| 驱动 | 会出现待核对 | 文件身份与恢复限制 |
|---|---|---|
| 阿里云盘 `aliopen` | 会 | 创建后可知 ID，但获取地址失败前没有写回；父目录重复编码阻断核对；SHA1 原本在支持范围内。 |
| PikPak `pikpak` | 会 | 创建后写回 ID；统一文件元数据没有填充可用的 MD5/SHA1/SHA256。上传失败还可能已成功清理远端文件，公共回执仍保守显示未知。 |
| OneDrive `onedrive` | 会 | ID 通常来自最终完成响应；内部会话查询和分片恢复较完整，但队列普通恢复不会进入驱动续传。SHA1 可核对，QuickXorHash 当前不支持。 |
| Dropbox `dropbox` | 会 | ID 依赖最终提交响应；专有 `dropbox` 哈希不在公共核对范围。存在 F12/F14。 |
| 123 云盘 `pan123` | 会 | 分片前写回 ID；统一模型明确清空 ContentHash，公共核对仍无法完成。存在 F13/F14。 |
| 普通蓝奏 `lanzou` | 会 | 上传成功路径也不写回统一文件 ID；统一元数据无可用内容哈希。 |
| 优享蓝奏 `ilanzou` | 会 | ID 依赖秒传命中或最终结果轮询；直接 GetFile 为缺少大小、内容哈希的简化模型。 |
| 移动云盘 `pan139` | 会 | 个人云在正常完成后才写回 ID；SHA256 可用于核对，但完成回执丢失时往往没有 ID。家庭云上传不写回统一 ID。 |
| 天翼云盘 `pan189` | 会 | ID 依赖最终 commit 返回；MD5 可用，但 commit 回执丢失时通常没有 ID。 |
| 一刻相册 `yike` | 会 | 有 fsid 和相册信息，但没有写回统一上传 FileID；加入相册失败也会进入未知状态，即使文件已上传。 |
| 光鸭 `guangya` | 会 | ID 依赖上传完成后的任务轮询；轮询超时或失败时没有文件 ID。元数据的 MD5 不能补足缺失身份。 |
| WebDAV `webdav` | 会 | PUT 成功后才写回可推导的目标路径；没有将 ETag 冒充内容哈希。当前普通自动核对不可用。 |
| S3 `s3` | 会 | 成功后才写回可推导的对象 ID；没有向统一模型提供可核对内容哈希，不能把 multipart ETag 当成 MD5。 |
| 迅雷 `thunder` | 正常入口不适用 | 当前能力明确关闭上传。 |

公共队列的普通刷新按钮只调用 `reconcileUpload`；遇到非空 attempt 时不会重新进入驱动。因此，驱动自身“支持分片续传”不等于用户能通过普通重试恢复。用户选择“核对后重试”后才清空 attempt 并重新进入驱动；是否复用同一会话取决于具体驱动。这个按钮不保证每个网盘都会从已上传分片继续。

7 项探针全部通过，表示**确认这些缺陷存在**，不是上传功能通过验收。网络响应和存储失败均为隔离注入，没有访问实际账号，没有执行真实覆盖。修复后应改写为断言正确行为的回归测试，不应继续把缺陷表现当作通过标准。

## 5. 修复顺序与边界

先修复 F8 的目录 ID 映射和 F12 的 skip 覆盖窗口。随后处理 F9/F10，让未提交、明确拒绝和回执未知有不同状态，并恢复原始错误可见性。接着补齐 F11 的持久身份、实际文件名和逐盘核对能力，再统一 F13/F14/F15。

不能用删除 `UPLOAD_RESULT_UNKNOWN`、无条件清空 attempt 或把所有错误直接重试来解决截图问题。这样会丢掉已有防重保护。需要分别核验：上传前失败、初始化成功后失败、部分分片成功、完成回执丢失、凭据或回执保存失败、进程重启、同名写入和相册后置操作失败。

用户确认截图对应远端秒传成功。本轮修复了可以导致客户端误判的协议与回执路径，但没有重放用户的原始远端响应，不能将某一个代码分支认定为该历史任务的唯一原因。项目其他发现与构建结果见总报告。
